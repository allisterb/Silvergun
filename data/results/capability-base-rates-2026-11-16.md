## Reading this

- **These are facts, not verdicts.** A capability means the package calls an API in that category; nothing here
  gates. The point is base rates: how common each capability is in benign code, so a finding can be read in context.
- **Lib / any:** the first number counts packages with a finding in any assembly; the number after the slash counts
  only `lib/` assemblies (what a consumer's code loads). C-build is 0 after the slash by construction: its code
  lives in `analyzers/`, `build/` and `tools/`.
- **Coverage gaps, not zeros:**
  - Meta-packages with no assemblies of their own are scanned as empty; their code is in dependencies, which this
    offline run does not resolve. C-suspect: IronPdf, Microsoft.ClearScript, SQLitePCLRaw.bundle_e_sqlite3. C100+:
    MimeKit 5.0.0, SQLitePCLRaw.bundle_e_sqlite3.
  - Native binaries are not analysed. They appear in the JSON as skipped files ("not a valid CLR module"), not as
    findings: 86 in C100+ and C-suspect together, e.g. Playwright's bundled node executable, chromedriver,
    `tools/*.exe`. Native-only packages (Microsoft.ML.OnnxRuntime, Selenium.WebDriver.ChromeDriver,
    SQLitePCLRaw.lib.e_sqlite3) therefore show no capabilities at all.
- **Headline:** in benign top-200 code, process execution is in 16% of packages, network in 23%, registry in 6%,
  dynamic code loading in 44%. Indicator `RawCodeHost` is 0 of 200. In the suspect corpus every capability is 38-84%,
  as chosen. A capability alone separates little; what separates is the combination, the arguments (SSA values)
  and the gate's rules, which are measured elsewhere (`behaviour-recall-2026-11-15.md`).
