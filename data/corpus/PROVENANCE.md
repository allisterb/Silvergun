## Version pinning method (hand-rolled SemVer — 5.1 has no `[SemanticVersion]`)

For each candidate package id, `GET {PackageBaseAddress}{id-lower}/index.json` returns every listed
version. `ConvertTo-SemVerParts` **excludes any version with a `-prerelease` tag outright** (returns
`$null`, never string-compared), then `Select-HighestStableVersion` compares the remainder as plain
**integer** `major`/`minor`/`patch[.revision]` tuples — `[version]` is never used anywhere in this
script, because it cannot represent prerelease tags and mis-sorts them.

**Synthetic evidence** (printed by every run, `Show-SemVerEvidence`):

```
input:  9.0.0, 9.5.2, 10.0.0, 2.1.0, 10.0.0-preview.1
semantic pick (this script, correct):         10.0.0
lexical string-sort pick (wrong, for contrast): 9.5.2
```

**Real-package evidence, across the actual 9.x/10.x boundary** (`Microsoft.Extensions.DependencyInjection`,
175 versions on record as of 2026-08-20):

```
highest stable pick (this script):              10.0.11
lexical string-sort pick (wrong, for contrast): 9.0.9
```

A lexical sort of that same version list would have pinned `9.0.9` — nine major versions and dozens
of patch releases behind the actual latest stable release. The manifest generator does not do this;
`10.0.11` is what both manifests actually pin wherever this package (or any other package that has
shipped both a 9.x and a 10.x stable release) was selected.

## `benign-top.manifest` — the scale corpus

**Method:** page the `SearchQueryService` with an **empty query** (`q=`), `prerelease=false`,
`semVerLevel=2.0.0`, `take=100`, `skip=0,100,200,…,900` (10 pages → 1000 candidate hits, deduplicated
by id keeping the maximum `totalDownloads` seen). Candidates are then ranked by `totalDownloads`
descending (ties broken ordinally by id), and taken in ranked order, resolving each one's highest
stable version via `PackageBaseAddress` until 100 packages have a resolvable stable version.

**Exact queries used** (10, one per page):
`GET {SearchQueryService}?q=&take=100&skip={0,100,...,900}&prerelease=false&semVerLevel=2.0.0`

**Result:** 1000 distinct candidate ids collected; **all first 100, ranked by totalDownloads, resolved
successfully on the first try** (0 skipped for "no stable version"). Final manifest: **100 packages**,
sorted ordinally by id per the script's determinism rule (this is why the file's order differs from
the hand-curated `tests/.../benign-corpus.manifest`, which instead preserves *append order* so that
`--take N` stays comparable as packages are added over time — a script-generated manifest has no such
history to preserve, so ordinal sort was chosen instead for reproducibility independent of the
search API's response order).

Top of the ranking (by `totalDownloads`, as returned 2026-08-20):

## Reproducibility notes

- **Regenerating either manifest invalidates comparability with prior runs.** Because packages get new
  releases and download counts change continuously, re-running `Get-Corpus.ps1` against a cold cache
  at a later date will very likely select a different candidate set and/or different pinned versions.
  A manifest's `CorpusManifest.Hash` (computed by the harness over the normalized entry list) is what
  ties a measurement report to the exact package set it was computed over — quote it, don't assume the
  file path alone identifies the corpus.
- **This manifest's entry order is ordinal-by-id, not append order** — unlike the hand-curated
  `tests/Silvergun.CodeAnalysis.IL.Tests.BenignCorpusHarness/benign-corpus.manifest`, whose order is
  meaningful (`--take N` keeps the first N, and new packages are appended so older `--take` subsets
  stay comparable across time). A script-generated manifest has no such curation history to preserve,
  so ordinal sort was used instead, for output determinism independent of the live search API's
  response ordering (which is not guaranteed stable over time).
- Re-running with `-Take` set to a value smaller than the built-in defaults (100 / ~8-per-category) is
  useful for a quick smoke test but produces a **different, non-comparable** manifest — the take-3/7
  smoke-test manifests generated during this task's verification were overwritten by the full runs
  and are not what ships.

## What the API did not let us do cleanly

- **No documented "sort by downloads" parameter.** `SearchQueryService` has no `sortBy`; ranking by
  `totalDownloads` had to be done client-side over a paged sample (1000 hits from an empty query),
  not requested directly from the API. This is disclosed rather than worked around by scraping
  nuget.org's website (which does support such sorting in its UI but is not the documented v3 API).
- **No way to ask "does this package's description mention X" server-side beyond free-text relevance
  search** — `q=` is a relevance search over id/description/tags, not a semantic filter, so some
  adversarial-category search terms surfaced borderline-relevant results (e.g. `AWSSDKCPP-Core` is a
  C++ wrapper published to NuGet, which the harness may report as `no-scannable-tfm` rather than a
  managed-code finding; that is itself valid data for the downstream measurement, not a defect in this
  script — packages were not hand-filtered post-search to avoid such outcomes, per the spec's explicit
  instruction not to hand-pick toward a cleaner-looking corpus).
